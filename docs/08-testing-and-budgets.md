## 1. ชั้นของการทดสอบ

| ชั้น | ที่ไหน | ทดสอบอะไร | ต้องเร็วแค่ไหน |
|---|---|---|---|
| Unit | `refx-core` | layout algorithm, command/undo, arena, geometry | < 2 s ทั้งหมด |
| Property | `refx-core` (`proptest`) | undo(apply(x)) == x, layout ไม่คืน NaN | < 30 s |
| Integration | `refx-io`, `refx-asset` | save/load round-trip, journal recovery, cache hit/miss | < 20 s |
| Fuzz | `fuzz/` | decoder, document parser, journal, layout | nightly |
| Golden image | `refx-render` | render off-screen เทียบภาพอ้างอิง | < 60 s |
| Benchmark | `benches/` | frame time, memory, startup | ทุก PR |
| Manual | checklist | device lost, drag&drop, ปิดเครื่องกลางคัน | ก่อน release |

### Property test ที่ต้องมี (คุ้มที่สุด)

```rust
// 1. undo คืนสภาพเดิมเป๊ะเสมอ — นี่คือหัวใจของ I-3
proptest! { fn undo_restores_exactly(cmds: Vec<AnyCommand>) {
    let before = board.snapshot();
    for c in &cmds { history.apply(c); }
    for _ in &cmds { history.undo(); }
    assert_eq!(before, board.snapshot());
}}

// 2. layout ไม่เคยคืนค่าที่ไม่ finite ไม่ว่า input จะบ้าแค่ไหน
proptest! { fn layout_always_finite(items: Vec<ItemAspect>, p: LayoutParams) {
    for (_, pos, size) in layout(&items, &p) {
        assert!(pos.is_finite() && size.is_finite() && size.x > 0.0);
    }
}}

// 3. save → load ได้ของเดิม
proptest! { fn roundtrip(board: Board) {
    assert_eq!(board, load(&save(&board)?)?);
}}

// 4. layout เป็น deterministic
proptest! { fn layout_deterministic(items: Vec<ItemAspect>, p: LayoutParams) {
    assert_eq!(layout(&items, &p), layout(&items, &p));
}}
```

> ### ★ `startup_to_window` วัด **warm** — และ cold คือคนละเรื่องที่ต้องรู้ (27 ส.ค. 2026)
>

>
> ความต่างคือเวลาที่ OS ต้องอ่าน binary 17 MB เข้า file cache — **ไม่ใช่ flake ที่ควรเฉลี่ยทิ้ง**
> มันคือสิ่งที่ผู้ใช้เจอจริงตอนเปิดโปรแกรมครั้งแรกหลังติดตั้งหรืออัปเดต
>
> | | วัดอะไร | เพดาน |
> |---|---|---|
> | **warm** (ค่าในตาราง) | การเปิดครั้งที่สองเป็นต้นไป = เกือบทุกครั้งที่ผู้ใช้เปิด | **400 ms** |

>
> **ไม่ตั้งเพดาน cold ตอนนี้** เพราะมีข้อมูลจากเครื่องเดียวและมันขึ้นกับดิสก์ของผู้ใช้มาก
> (SSD vs HDD ต่างกันหลายเท่า) การเดาตัวเลขคือสิ่งที่ทำให้ "1000 ภาพ 4 วินาที" ผิด 20 เท่า
>
> ★ **แต่รู้ตัวแปรที่คุมมันแล้ว: cold start โตตามขนาด binary**
> `binary_size` ที่บังคับใน CI อยู่แล้วจึงเป็นคันโยกของแถวนี้ไปในตัว —
> ถ้าวันหนึ่ง binary โตขึ้นมาก ให้ถือว่า cold start แย่ลงตามโดยไม่ต้องวัด

> **ต้องบังคับใน CI ไม่ใช่วัดด้วยมือ** — งบที่ไม่มีใครตรวจอัตโนมัติคืองบที่จะถูกละเมิดเงียบ ๆ

### ★ นโยบายการลดขนาด binary (28 ก.ค. 2026)

**ลำดับความสำคัญใน `CLAUDE.md` ยังบังคับอยู่: เสถียร → ปลอดภัย → เบา → ฟีเจอร์**
ขนาดไฟล์อยู่อันดับ **3** การลดขนาดที่แลกมาด้วยความเสถียรหรือความปลอดภัย = ไม่เอา

#### ห้ามเด็ดขาด

| ห้าม | เหตุผล |
|---|---|
| `panic = "abort"` | ทำให้ `catch_unwind` พัง → ภาพเสีย 1 ไฟล์ล้มทั้งโปรแกรม (**ผิด I-7**) มีคอมเมนต์เตือนไว้ใน `Cargo.toml` แล้ว |
| ตัด backend ของ wgpu จนเหลือตัวเดียว | เครื่องที่ driver มีปัญหาต้องมีทางถอย — Windows เก็บ **DX12 + Vulkan** · Linux เก็บ **Vulkan + GL** |
| ตัด format ภาพที่ผู้ใช้มีจริง | ดู `docs/05 §7` — เป็นการตัดฟีเจอร์ ไม่ใช่การ optimize ต้องถามก่อน |

#### ต้องวัดก่อนแก้เสมอ

`cargo bloat --release --crates` และ `--filter` ต่อ crate **ห้ามเดาว่าอะไรใหญ่**
เราเพิ่งเสียเวลาไปกับตัวเลข "12 MB" ที่ไม่มีใครวัด

#### เป้าที่ตรวจแล้วว่ามีจริง (เรียงตามความเสี่ยงต่ำ→สูง)

1. **dependency ที่ประกาศไว้แต่ไม่มีใครเรียก** — `zune-jpeg` (ยืนยันแล้วว่าไม่มีโค้ดไหนใช้)
   และ `memmap2` (ถอดออกจาก `refx-asset` แล้วตั้งแต่ห้าม mmap แต่ยังค้างใน `[workspace.dependencies]`)
   *ความเสี่ยง: ไม่มี* — ถ้า `image` ดึง `zune-jpeg` เข้ามาเองอยู่แล้ว ขนาดจะไม่ลด แต่ก็ควรลบเพื่อความชัดเจน
2. **backend ของ wgpu ที่ build ไม่ได้ใช้** — เช่น Metal บน Windows/Linux
   ตัดแบบ per-OS ได้โดยไม่เสียทางถอย · น่าจะเป็นก้อนใหญ่ที่สุด
3. **format ภาพที่แทบไม่มีใครใช้** — `tga` (แทบไม่เจอในงานนักวาด) และ `bmp`
   `tiff` **ให้เก็บไว้** (สแกนงานจริงใช้) และมันคือ decoder ที่ควร fuzz ที่สุด
   → ตัด `tga`/`bmp` ต้องแก้ `ALLOWED_FORMATS` + ข้อความ error + `docs/05 §7` พร้อมกัน
4. ~~**`rusqlite` feature `bundled`** น่าจะเป็นก้อนใหญ่อันดับต้น ๆ~~
   **วัดแล้ว 15 ก.ย. 2026: `rusqlite` + `libsqlite3-sys` = 80.5 KiB เท่านั้น**
   → **ไม่ใช่เป้า** · ห้ามเปลี่ยนไปใช้ SQLite ของระบบอยู่ดี (Windows ไม่มีให้ใช้)
   > ★ ข้อนี้เป็นการเดาที่เขียนไว้ในหัวข้อที่ชื่อว่า **"ต้องวัดก่อนแก้เสมอ"**
   > — นโยบายจับตัวเองได้ · ตัวเลขที่ยังไม่ได้วัดต้องเขียนว่า "ยังไม่วัด" ไม่ใช่ "น่าจะ"

### ★★★ ไฟล์ที่ **สร้างขึ้น + commit + มีประตูคุม** ต้องเหมือนกันทุกไบต์ทุก OS

17 ก.ย. 2026: `licenses --check` **แดงบน Linux** กับไฟล์ที่สร้างบน Windows
→ ประตูกลายเป็นภาษีของแพลตฟอร์ม: ใครสร้างไฟล์บน OS ไหน CI ของอีก OS ก็แดง
แล้วทางแก้ที่คนจะเลือกคือ **ปิดประตู** ซึ่งแย่กว่าไม่เคยมีประตู

**ไฟล์ที่สร้างต้องเป็นฟังก์ชันของ `Cargo.lock` + registry เท่านั้น ไม่ใช่ของเครื่อง**
สามอย่างที่ทำให้มันไม่เป็นแบบนั้น เรียงตามความน่าจะเป็น:

| ต้นเหตุ | วิธีตัดออก |
|---|---|
| **dependency ต่างตามแพลตฟอร์ม** (`windows-sys` ฯลฯ) — `cargo tree` ให้ผลตามเครื่องที่รัน | ระบุ `--target` **ทุกแพลตฟอร์มที่รองรับ** อย่างชัดเจน แล้วรวมผล · ห้ามพึ่ง host |
| **การเรียงลำดับขึ้นกับ locale** | เรียงแบบ **เทียบไบต์** เสมอ ไม่ใช่ตัวเปรียบเทียบของภาษา |
| **line ending** | เขียน `\n` ตรง ๆ · `.gitattributes` มี `*.md text eol=lf` อยู่แล้ว แต่ตัวสร้างต้องไม่พึ่งข้อนั้น |

> ★ และประตูที่แดงต้อง **บอกว่าอะไรต่าง** — บรรทัดแรกที่ไม่ตรง + เลขบรรทัด + จำนวน
> ประตูที่บอกแค่ "ไม่ตรง" ทำให้คนเสียเวลาเท่ากับตอนไม่มีประตู
> และผลักให้เลือกทางที่ง่ายที่สุดคือปิดมันทิ้ง
   → **วัดว่ามันกินเท่าไหร่ แล้วรายงาน ยังไม่ต้องแก้**
5. `opt-level = "s"` หรือ `"z"` — **ทางเลือกสุดท้าย ต้องวัดคู่กับ benchmark เสมอ**
   decode ใช้เวลา ~81 ms/ไฟล์อยู่แล้ว ถ้าช้าลงอีกเพื่อประหยัดไม่กี่ MB ถือว่าขาดทุน

รายงานเป็นตาราง **ก่อน/หลัง ทั้งขนาดและ benchmark** ทุกครั้ง

   → I-4 พูดถึงไฟล์ที่ *ตั้งใจโจมตี* ไม่ใช่แค่ไฟล์ที่ *เสียหาย* — เทสต์ต้องสะท้อนข้อนั้น

   > ### ★★ รูปแบบเดียวกันนอกเรื่องความปลอดภัย: **input ต้องไปถึงกิ่งที่กำลังทดสอบได้จริง**
   >
   > เคสจริง (P5-3b): เทสต์ Dvorak ที่คุม *"logical ต้องชนะ physical"* ยิงด้วย
   > `KeyCode::Period` ซึ่ง **ไม่มีในแผนที่ physical เลย** → ตาข่ายรองคืน `None` ทุกกรณี
   > ผลจึงตกกลับเป็น logical เสมอ **ไม่ว่ากฎจะเป็นแบบไหน**
   >
   > พิสูจน์แล้วว่ามันจับไม่ได้: NC ที่ให้ *physical ชนะเสมอ* → **เทสต์เดิมเขียว** ทั้งที่กฎพังแล้ว
   >
   > → ก่อนเชื่อว่าเทสต์คุมกิ่งไหน **ต้องรู้ว่า input ของมันไปถึงกิ่งนั้นได้** —
   >   คีย์ที่ไม่อยู่ในตาราง · path ที่ตกด่านแรก · ไฟล์ที่ตกที่ checksum
   >   ล้วนทำให้เทสต์ "ผ่านโดยไม่เคยแตะสิ่งที่ชื่อมันอ้าง"
   > → วิธีตรวจที่ถูกคือ **NC ที่ทำให้กิ่งนั้นพัง แล้วดูว่าเทสต์แดงไหม** ไม่ใช่การอ่านโค้ดเทสต์

2. **โครงเปล่าห้ามเงียบ** — target/เทสต์/job ที่ยังไม่ได้ต่อกับโค้ดจริง
   ต้องทำให้ CI **แดง หรือ ข้ามอย่างชัดเจน** ห้ามรันแล้วผ่านแบบว่างเปล่า
   *สัญญาณที่โกหกแย่กว่าไม่มีสัญญาณ* เพราะมันปิดโอกาสที่จะมีใครกลับมาดู
3. **ทุกไดเรกทอรีที่มี `Cargo.toml` ต้องถูก lint** ถึงจะอยู่นอก workspace ก็ตาม
   (`fuzz/` เคยหลุดเพราะ `exclude` — ปิดด้วย job `fuzz-lint` แล้ว · ตอนนี้ CI
   บังคับด้วยกลไกแล้ว ข้อนี้จึงเป็นบันทึกว่า**ทำไม**มีกลไกนั้น)
4. **ชุดที่รันในเครื่องกับที่ CI รัน ต้องเป็นชุดเดียวกัน — ทั้งสองทิศ**

   ถ้า CI อ่อนกว่า "CI เขียว" แปลว่าน้อยกว่าที่ทุกคนเข้าใจโดยไม่มีใครรู้ตัว ·
   **ถ้าเครื่องอ่อนกว่า** ทุกการค้นพบจะถูกเลื่อนไปอยู่ใน CI ซึ่งช้ากว่าหลายสิบเท่า

   > ### ★★★ รูปธรรมของข้อนี้: **ประตูทุกบานที่บล็อกได้ ต้องอยู่ในรายการก่อน commit**
   > ไม่งั้นมันไม่ใช่ประตู **มันคือเซอร์ไพรส์**

   > แต่ไม่อยู่ในรายการก่อน commit → การขยับเวอร์ชันทำให้ **แดงสองรอบ CI**

   >
   > ★★ ข้อ 4 ถูกเขียนไว้ตั้งแต่ต้นและ **ไม่เคยถูกอ้างเลยสักครั้ง** — ไม่ใช่เพราะ
   > ไม่จำเป็น แต่เพราะ **เขียนนามธรรมเกินกว่าจะหยิบ** · รูปธรรมของมันไปเกิดใหม่
   > เป็นกล่องใต้ข้ออื่นแทน แล้วก็ยังโดนละเมิดอยู่ดี
   > → **กฎที่ไม่มีตัวอย่างรูปธรรม = กฎที่ไม่มีใครนึกออกตอนที่ต้องใช้**
5. **งานที่ผู้ใช้มองเห็น ต้องมีภาพหน้าจอจริงก่อนบอกว่าเสร็จ** (ดู `docs/03 §1`)

   >

   > ★ **ทำไมข้อนี้ถึงคุ้มแม้ต้นทุนต่อ task จะสูง** — เพราะมันเป็นเครื่องมือเดียวที่จับ
   > **"ทุกชิ้นถูก แต่ประกอบผิด"** ได้ ซึ่งเป็นคนละชนิดกับสองข้อล่าง:

   > สิ่งที่ผิดอยู่ระหว่างชิ้น ซึ่งไม่มีเทสต์ตัวไหนเป็นเจ้าของ

   > **ห้ามตัดข้อนี้ทิ้งเพราะมองว่าเป็นพิธีกรรมที่แพง**
5b. **★ ห้าม assert เวลานาฬิกา — assert "งานที่ทำ" แล้ว *พิมพ์* เวลาแทน**

   ซึ่งอันตรายกว่าไม่มีเทสต์

   → เวลายังพิมพ์ไว้ได้เพื่อดูแนวโน้ม แค่อย่าเอาไปตัดสินผ่าน/ไม่ผ่าน
5c. **★ คำกล่าวอ้างว่า "ปิดช่องแล้ว" ต้องชี้ไปที่เทสต์ที่รักษามันไว้**
   ถ้าชี้ไม่ได้ มันคือ *ความหวัง* ไม่ใช่ *การปิดช่อง* และจะกลายเป็นข้อมูลเท็จในเอกสาร

   **แต่ `on_wake()` ไม่มีกิ่งไหนรับ** พอคืน `None` ก็หลับยาวต่อ
   → กลไกทั้งชุด **ไม่เคยทำงานเลยสักครั้ง** ขณะที่เอกสารบอกว่าเรียบร้อย

   → ทุกครั้งที่เขียนใน `HANDOFF` ว่าปิดช่องอะไรไปแล้ว **ต้องระบุชื่อเทสต์กำกับ**
   → ถ้าเป็นเรื่องที่เทสต์คุมไม่ได้ (ต้องรันจริง) ให้เขียนว่า *"ยืนยันด้วยมือเมื่อ <วันที่>"*
     ไม่ใช่ *"ปิดแล้ว"* — สองอย่างนี้ให้ความมั่นใจต่างกันมาก
   → เจอข้อความในเอกสารที่รู้แล้วว่าไม่จริง **ให้แก้ทันที** อย่ารอรอบถัดไป

6. **ตัวเลขที่วัดครั้งเดียวแล้วจดไว้ จะเสื่อมสภาพเงียบ ๆ**
   ตัวอย่างจริง: "atlas เติมกลับ **100/100** ใน 0.99 ms" ถูกจดไว้ตอนวัดและเป็นความจริงตอนนั้น
   แต่พอเพิ่ม lazy allocation ทีหลัง atlas ที่เพิ่งสร้างมี 0 layer → ของจริงกลายเป็น **0/8**
   โดยไม่มีอะไรส่งเสียง ตัวเลขในเอกสารยังบอก 100/100 อยู่หลาย session
   → **คุณสมบัติที่สำคัญพอจะจดตัวเลขไว้ ต้องสำคัญพอที่จะมีเทสต์คุม**
   ตัวเลขในเอกสารคือ *ภาพถ่าย ณ เวลานั้น* ไม่ใช่คำรับประกัน
7. **เทียบประสิทธิภาพ ต้องวัดสองฝั่งบนเครื่องเดียวกันในเซสชันเดียวกัน**

8. **★ สัญญาที่ถูกต้องเฉพาะเมื่อผู้เรียกเรียก "ถูกจังหวะ" คือกับดัก**

   2. **เทสต์:** ถ้าสัญญามีเงื่อนไขเรื่องเวลา **ต้องมีอย่างน้อยหนึ่งเทสต์ที่เรียกแบบ *เลื่อนออกไป*

10. **★ ทุกอย่างที่โปรแกรม *ประกาศว่ารองรับ* ต้องถูกทดสอบจริงอย่างน้อยหนึ่งครั้ง**
    เครื่องที่เราพัฒนาอยู่คือ **หนึ่งสภาพแวดล้อม** ไม่ใช่ทั้งหมด
    มิติที่ต่างกันแล้วไม่มีใครสังเกต = โค้ดที่ไม่เคยถูกรันเลยแม้แต่ครั้งเดียว

    เกิดมาแล้วสองครั้ง คนละมิติ:

    | ประกาศว่ารองรับ | ความจริง | เจอตอน |
    |---|---|---|
    | Linux (CI matrix มี ubuntu) | โค้ด `#[cfg(target_os = "linux")]` **ไม่เคยถูกคอมไพล์เลย** | CI รันครั้งแรก (1 ส.ค.) |
    | **ภาษาไทยเป็นภาษาที่สอง** (`docs/03 §0`) | **คีย์ลัดทุกตัวใช้ไม่ได้บน layout ไทย** มาตั้งแต่ P2-4 | 6 ส.ค. |

    ตัวหลังมองไม่เห็นเพราะทุก session อยู่บน layout อังกฤษ — matcher ดูแต่ *logical key*
    ซึ่งบน layout ไทยปุ่ม `C` ส่ง `แ` มา ผู้ใช้ไทยจึงกดคีย์ลัดไม่ได้เลยสักปุ่ม

    → **ทำรายการว่าเราประกาศรองรับอะไรบ้าง** (OS · ภาษา · layout · ชนิด GPU · ขนาดจอ)

    → **เป็นไปไม่ได้ที่ทั้งคู่จะทำงานหรือทั้งคู่จะไม่ทำงาน**

    | วิธีคุม | อยู่ได้นานแค่ไหน |
    |---|---|
    | คอมเมนต์ว่า "ห้าม…" | จนถึงคนถัดไปที่ไม่ได้อ่าน |
    | เทสต์/ประตูที่ตรวจว่าไม่มีใครทำ | จนถึงทางเข้าที่ประตูมองไม่เห็น |
    | **ชนิดข้อมูลที่ทำให้เขียนไม่ออก** | **ตลอดไป — และไม่ต้องมีใครจำ** |

    → เมื่อกฎข้อไหนสำคัญพอจะเขียนลง spec **ให้ถามก่อนเสมอว่ามันกลายเป็น
      ข้อผิดพลาดตอนคอมไพล์ได้ไหม** · ได้เมื่อไหร่ กฎข้อนั้นเลิกต้องมีคนเฝ้า

20. **★★ เครื่องมือวิเคราะห์ห้ามแก้ working tree ของจริง — ไม่ว่ากรณีใด**

    12 ก.ย. 2026 · ตัวรัน mutation แก้ไฟล์ซอร์สจริงแล้วคืนค่าเมื่อจบ
    → **กด Ctrl+C กลางคัน = ไฟล์ของผู้ใช้ค้างอยู่ในสภาพที่ถูกดัดแปลง**
    และรอบนั้นกินเวลาหลายชั่วโมง ซึ่งเป็นช่วงที่คนกดหยุดมากที่สุด

    รูปเดียวกับ I-3 แต่เกิดกับซอร์สแทนที่จะเป็นงานผู้ใช้: **สิ่งที่กู้คืนใน
    `finally` กู้ไม่ได้เมื่อโปรเซสไม่ได้เดินไปถึงบรรทัดนั้น**

    → ทำงานบน **สำเนา** เสมอ (worktree หรือโฟลเดอร์ชั่วคราว)
    → ★ เกณฑ์ทั่วไป: เครื่องมือที่ *ต้องการ* การเก็บกวาดเพื่อความถูกต้อง
      ออกแบบผิดตั้งแต่ต้น · ที่ถูกคือออกแบบให้ **ไม่มีอะไรต้องเก็บกวาด**

    > ### ★★★ ตัวกวาด mutation ต้องรันบน **OS ที่โค้ดนั้นถูกคอมไพล์จริง** (13 ก.ย. 2026)
    > ตัวกวาดหาด่านด้วยการอ่าน **ข้อความในซอร์ส** แล้วแทรกบรรทัดเข้าไป
    > ครึ่งหนึ่งของ `refx-platform` อยู่หลัง `#[cfg(target_os = "windows")]`
    > → บน ubuntu การแทรกลงไปในฟังก์ชันที่ **ไม่ได้ถูกคอมไพล์** ไม่เปลี่ยนอะไรเลย
    > เทสต์เขียว และด่านทุกตัวในนั้น **รายงานว่า "รอด" ด้วยเหตุผลที่ไม่เกี่ยวกับเทสต์**
    >
    > แล้วเราจะอ่านตัวเลขนั้นว่า *"ไม่มีใครเทสต์ส่วนนี้"* ซึ่งผิดคนละเรื่อง —
    > **ประตูโกหกโดยให้ตัวเลขที่ดูน่าเชื่อ** (`ข้อ 9`)
    > → matrix ต้องผูก `os` กับ crate · `refx-platform` = `windows-latest`
    >   คูณสองของ Windows คุ้มเสมอเมื่อทางเลือกคือตัวเลขที่อ่านผิด

    > ### ★★ "ข้าม" ไม่ใช่ "ผ่าน" — บรรทัดสรุปต้องแบกทั้งสามตัวเลข
    > `refx-asset` มี 2 ด่านที่คอมไพล์ไม่ผ่านหลังแทรก (`if let Some(x) = … { return f(x); }`
    > — body ที่แทรกอ้างตัวแปรที่ยังไม่เกิด) · ตัวกวาดพิมพ์ `ข้าม` ระหว่างทางจริง
    > แต่บรรทัดสรุปเขียนแค่ `รอดจากทุกเทสต์: 0` ซึ่ง **อ่านได้ว่าครบ**
    > → สรุปต้องมี **ค้นเจอ / ทดสอบ / ข้าม** เสมอ · รูปเดียวกับ `steps: N`

    > ★★ และเครื่องมือนี้จ่ายค่าตัวเองไปแล้วก่อนเริ่มใช้จริง — เจอ
    > `unreachable statement` ใน `command.rs` ที่ **clippy รันคู่กันมาตลอดแต่ไม่เห็น**
    > · เครื่องมือคนละชนิดเห็นคนละอย่าง ไม่ใช่ของซ้ำซ้อนกัน

## 4. Definition of Done (ทุก PR)

PR จะ merge ได้ต่อเมื่อ **ครบทุกข้อ**:

1. `cargo build --release` ผ่านบน Windows + Linux
2. `cargo clippy --all-targets -- -D warnings` ไม่มี warning เลย
3. `cargo fmt --check` ผ่าน
4. **`cargo nextest run --workspace --all-features`** ผ่าน — **ไม่ใช่ `cargo test --all`**
   · `--all` = *ทุก package* ไม่ใช่ *ทุก feature* → ข้ามเทสต์หลัง feature gate เงียบ ๆ
   · `cargo test` ไม่มี timeout → เทสต์ค้างกลายเป็นซอมบี้แทนที่จะแดงพร้อมชื่อ
   · **CI รัน nextest มาตลอด** ข้อนี้เคยสั่งของที่อ่อนกว่าที่ CI ตรวจจริง 10 ตัว
   (แก้ 13 ก.ย. 2026 — CC รายงานว่าสเปกขัดกันเองสองรอบติด · รายละเอียดที่ `§3.9 ข้อ 9`)
   · ★ **เทียบจำนวนเทสต์กับรอบก่อนทุกครั้ง** ส่วนต่างที่อธิบายไม่ได้ = ยังไม่ผ่านข้อนี้
5. `cargo deny check` ผ่าน
6. Benchmark ที่เกี่ยวข้องยังอยู่ใต้เพดานสัมบูรณ์ (กฎ 10% ถูกยกเลิกแล้ว — ดู §2)
7. โค้ดใหม่ไม่มี `unwrap()` / `expect()` / `panic!()` บนเส้นทางที่ข้อมูลมาจากผู้ใช้หรือจากไฟล์
   *(ในเทสต์ใช้ได้ ในโค้ดที่เป็น invariant ภายในใช้ `expect("เหตุผลชัดเจน")` ได้)*
8. ไม่มี `unsafe` นอก `refx-platform`
9. ทุก path ที่แตะดิสก์ผ่าน `validate_path`
10. ทุก mutation ของ `Board` ผ่าน `Command` (ไม่มี `&mut board` หลุดออกไปที่อื่น)
11. ถ้าเพิ่ม image format → ต้องมี fuzz target มาด้วยใน PR เดียวกัน
12. ถ้าแก้ file format → ต้องมี migration + fixture ไฟล์เก่ามาด้วย
13. `cargo tree -d | grep '^png'` **ต้องว่าง** (บังคับใน CI job `single-wgpu` ด้วย)

    > ★★ P5-4 ตรึง `png` ตรง ๆ เพื่อเขียน PNG ทีละแถบ (`image` ไม่มี API สตรีมสำหรับ PNG
    > — ดู `docs/07 §6` และ `docs/09`) · ถ้าเวอร์ชันที่เราตรึง**เลื่อนออกจากที่ `image` ใช้**
    > จะได้ png สองก๊อปปี้ในทรี: binary โตฟรี ๆ และมี **ตัวเข้ารหัสสองตัวที่อาจให้ผล
    > ไม่เหมือนกัน** ระหว่าง export กับ spool · `^` สำคัญ — ไม่งั้นจับ crate ลูกที่ชื่อ
    > ลงท้ายด้วย png ติดมาด้วย · เป็นข้อเดียวกับประตู `^wgpu` ที่มีอยู่แล้ว

## 5. Logging

```rust
tracing::info!  // เหตุการณ์ระดับผู้ใช้: เปิด/บันทึกไฟล์, สลับ mode
tracing::warn!  // กู้คืนได้: decode ล้ม, ไฟล์หาย, cache miss ผิดปกติ
tracing::error! // เสียหาย: save ล้ม, device lost, DB เปิดไม่ได้
tracing::debug! // ปิดใน release
```

- Log ไปที่ `<cache_dir>/logs/` หมุนไฟล์ที่ 5 MB เก็บ 3 ไฟล์
  **`tracing-appender` 0.2 หมุนตามขนาดไม่ได้** (รองรับแค่ minutely/hourly/daily)
  ต้องเขียน writer เองแล้วห่อด้วย `non_blocking` — ห้ามใช้ daily แทน เพราะ error ที่วนซ้ำ
  ทำให้ไฟล์เดียวโตระดับ GB ได้ภายในวันเดียว
- **ห้ามเขียน log ลง stderr ใน release** — `windows_subsystem="windows"` ไม่มี console
  และการเขียน stderr เกิดบน UI thread (ผิด I-2)
- **cache eviction ห้ามแตะโฟลเดอร์ `logs/` เด็ดขาด** — crash log คือสิ่งเดียวที่ผู้ใช้มีให้ส่งเวลารายงานปัญหา
  ถ้าโดนล้างพร้อม thumbnail cache เราจะ debug ปัญหาของผู้ใช้ไม่ได้เลย
- **ห้ามมี path เต็มใน log ระดับ info** (มีชื่อผู้ใช้อยู่ในนั้น) ใช้ชื่อไฟล์อย่างเดียว
- ต้องมีเมนู "เปิดโฟลเดอร์ log" ให้ผู้ใช้ส่ง log เองเวลารายงานปัญหา

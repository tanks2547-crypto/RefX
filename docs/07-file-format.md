# 07 — File Format & Persistence

crate: `refx-io`

## 1. โครงไฟล์ `.refx`

Container แบบง่ายที่สุดที่ยังทำงานถูก: header + chunk เรียงกัน (ไม่ใช้ zip — ตัด dependency และตัดช่องโหว่ zip-slip ทิ้งไปเลย)

```
┌──────────────────────────────────────────┐
│ magic     "REFX"          4 B            │
│ version   u16 = 1         2 B            │
│ flags     u16             2 B  (bit0 = packed)
│ doc_len   u64             8 B            │
│ doc_crc   u32             4 B  (crc32 ของ document)
├──────────────────────────────────────────┤
│ document  (postcard, บีบด้วย zstd -3)     │
├──────────────────────────────────────────┤
│ asset table  (มีเฉพาะ packed mode)        │
│   [hash:32B][offset:u64][len:u64][crc:u32] × n
├──────────────────────────────────────────┤
│ asset blobs  (ไฟล์ภาพต้นฉบับ ไม่แปลงอะไร)  │
└──────────────────────────────────────────┘
```

### ★★ Packed = version 2 · Linked ยังเป็น version 1 (ตัดสิน 12 ส.ค. 2026)

**ห้ามใช้ flag bit0 อย่างเดียวโดยคง version = 1** ถึงแม้จะเป็นทางที่ดูสะอาดกว่า

เหตุผลเดียวและมันเด็ดขาด: รุ่นเก่าที่เห็น `version = 1` จะ **เปิดไฟล์ได้สำเร็จ**
(มี `doc_len` จึงข้าม blob ท้ายไฟล์ไปเฉย ๆ ภาพขึ้นเป็น `Missing`)
แล้วถ้าผู้ใช้กด save รุ่นเก่าจะ **เขียน linked v1 ทับ → ภาพที่ฝังไว้หายถาวรทั้งหมด**

นั่นคือรูปแบบเดียวกับ `ColorLabel` ใน `docs/02 §2.9` แต่เกิดกับ **ทั้งไฟล์** ไม่ใช่ฟิลด์เดียว
และ `may_overwrite()` ช่วยไม่ได้เลย เพราะไฟล์อ่านได้ปกติในสายตารุ่นเก่า

| | packed = v2 | flag bit0 บน v1 |
|---|---|---|
| รุ่นเก่าเปิดไฟล์ packed | ปฏิเสธ พร้อมบอกให้อัปเดต | **เปิดได้ ภาพเป็น Missing** |
| รุ่นเก่า save ทับ | **ถูกกัน** (`may_overwrite`) | **ภาพฝังหายหมด** |
| รุ่นเก่าเปิดไฟล์ linked ปกติ | ได้ตามเดิม | ได้ตามเดิม |

**ห้ามดันทั้งสองโหมดเป็น v2** — จะทำให้ไฟล์ linked ธรรมดาที่รุ่นเก่าอ่านได้สบาย
กลายเป็นเปิดไม่ได้โดยไม่จำเป็น = ลงโทษผู้ใช้ที่ไม่เคยแตะ packed mode เลย

→ `FORMAT_VERSION` กลายเป็น **"อ่านได้ถึง 2"** ส่วน `encode` เขียน **1 สำหรับ linked · 2 สำหรับ packed**

> ข้อความตอนปฏิเสธต้องบอกว่า **ทำไม** ไม่ใช่แค่เลขเวอร์ชัน —
> *"ไฟล์นี้มีภาพฝังอยู่ข้างใน ต้องใช้ RefX รุ่นใหม่กว่าจึงจะเปิดได้"*
> เลขเวอร์ชันอย่างเดียวไม่บอกผู้ใช้ว่าเขาเจออะไร

### ★ จำนวนรายการของ asset table วางที่ไหน

**วางเป็นหัวเล็ก ๆ ที่ต้นบล็อก asset table เอง ไม่ใช่ในหัวไฟล์**

```
├──────────────────────────────────────────┤
│ asset table  (มีเฉพาะ packed mode)        │
│   count     u32   4 B            ← ★      │
│   table_crc u32   4 B            ← ★ crc32 ของ entry ทั้งชุด
│   [hash:32B][offset:u64][len:u64][crc:u32] × count
├──────────────────────────────────────────┤
```

**เหตุผลข้อ 1 — หัวไฟล์ต้องมีรูปร่างเดียวกันทุกเวอร์ชันตลอดไป**
ถ้าหัวไฟล์เปลี่ยนขนาดตามเวอร์ชัน จะต้องอ่าน version ก่อนถึงจะรู้ว่าหัวไฟล์ยาวเท่าไหร่
ซึ่งเป็นความซับซ้อนที่แลกมาโดยไม่ได้อะไร
ขนาด table = `8 + count × 52` → หาจุดเริ่ม blob ได้ทันทีโดยไม่ต้องแตะ document

**เหตุผลข้อ 2 — `table_crc` แยก "table เสีย" ออกจาก "document เสีย"**
เหตุผลเดียวกับที่ `doc_crc` มีอยู่: ผู้ใช้ที่ไฟล์งานเปิดไม่ขึ้นต้องรู้ให้ชัดว่าเกิดอะไร
document เสีย = งานหาย · table เสียแต่ document ดี = **โครงงานยังอยู่ครบ ขาดแต่ภาพ**
ซึ่งกู้ได้ด้วย relink คนละสถานการณ์และคนละข้อความ

> **ห้ามให้ผู้อ่านไล่ table จนกว่า offset จะชนท้ายไฟล์** — ไฟล์ที่ถูกตัดกลางทาง
> จะอ่านออกมาเป็น entry ปลอมได้ และ I-4 บังคับว่าต้องรู้ขอบเขตก่อนจอง

**ห้ามย้าย table เข้าไปอยู่ใน document ที่บีบด้วย zstd** ถึงแม้ `postcard` จะแถมความยาว
ของ `Vec` มาให้ฟรี — เพราะ `xtask dump-refx` (P4-8) และ relink ต้องอ่านรายการ asset ได้
โดยไม่ต้องคลายบีบทั้งเอกสาร และไฟล์ packed อาจใหญ่ระดับ GB

---

**สำคัญ:** `doc_crc` ทำให้แยกได้ว่า "ไฟล์เสียหายจากดิสก์" กับ "ไฟล์เวอร์ชันที่เราอ่านไม่เป็น" ซึ่งเป็นข้อความ error คนละแบบสำหรับผู้ใช้ — และผู้ใช้ที่ไฟล์งานเปิดไม่ขึ้นต้องการรู้ให้ชัดว่าเกิดอะไรขึ้น

## 2. สองโหมดการบันทึก

| | **Linked** (default) | **Packed** |
|---|---|---|
| เก็บภาพ | เก็บแค่ path + hash | ฝังไฟล์ต้นฉบับทั้งหมด |
| ขนาด | ~200 KB @ 1000 ภาพ | เท่าผลรวมภาพจริง |
| ใช้ตอน | ทำงานประจำวัน | ส่งให้คนอื่น / สำรอง / ย้ายเครื่อง |
| ภาพหาย | ต้อง relink | ไม่มีทางหาย |

Save As มีตัวเลือกนี้ชัดเจน และแถบสถานะบอกเสมอว่า board ปัจจุบันเป็นแบบไหน

### ★★★ ภาพที่ไม่มีไฟล์ต้นทาง ต้องถูกฝังเสมอ แม้ในโหมด Linked (ตัดสิน 13 ส.ค. 2026)

ภาพที่วางจาก clipboard **ไม่มีไฟล์ต้นทางบนดิสก์เลย** — มีอยู่แค่ใน RAM กับใน board
ถ้าบันทึกเป็น linked ตรง ๆ `AssetRef` จะชี้ไป path ที่ไม่มีอยู่จริง
→ เปิดกลับมาได้ `Missing` → **ภาพที่ผู้ใช้วางไว้หายถาวรโดยไม่มีอะไรเตือน**

นั่นคือ I-3 ถูกละเมิดแบบเงียบที่สุดเท่าที่จะเป็นไปได้

**กติกาที่ถูก — นิยาม "linked" ใหม่ให้ตรงกับความจริง:**

| โหมด | ทำอะไร |
|---|---|
| **Packed** | ฝังภาพ **ทุกใบ** |
| **Linked** | ลิงก์ใบที่มีไฟล์จริง · **ฝังเฉพาะใบที่ไม่มีไฟล์ต้นทาง** |

→ **`version = 2` แปลว่า "ไฟล์นี้มี asset ฝังอยู่"** ไม่ใช่ "ผู้ใช้เลือกโหมด packed"

> ### ★ ไม่เก็บ "ผู้ใช้เลือกโหมดไหน" ลงไฟล์ (ตัดสิน 21 ส.ค. 2026)
>
> ผลที่ตามมา: เอกสารที่มีแต่ภาพวางล้วน (ถูกฝังครบอยู่แล้วตามกฎข้างบน)
> จะเปิดกลับมาเป็น **packed** ทั้งที่ผู้ใช้ไม่ได้สั่ง
>
> **ยอมรับได้ และไม่แก้ด้วยการเพิ่มบิตในหัวไฟล์** เพราะ:
>
> 1. **มันไม่ผิด** — ไฟล์นั้นมี asset ฝังอยู่จริงทุกใบ เรียกว่า linked ต่างหากที่จะเป็นคำโกหก
> 2. **มองเห็นได้และกดกลับได้** — ตัวบ่งชี้บนแถบสถานะบอกโหมดตลอดเวลา
>    ไม่ใช่ความเปลี่ยนแปลงที่เกิดเงียบ ๆ
> 3. **รูปแบบไฟล์ควรบันทึก *ข้อเท็จจริง* ไม่ใช่ *ความตั้งใจ***
>    ข้อเท็จจริง ("มี blob อยู่ข้างใน") ตรวจสอบจากตัวไฟล์เองได้เสมอและไม่มีวันขัดกับเนื้อใน
>    ส่วนความตั้งใจ ("ผู้ใช้เลือก linked") เป็นแหล่งความจริงที่สอง ซึ่งจะเพี้ยนจากของจริง
>    ในวันที่ใครสักคนลืมอัปเดตมัน — แล้วเราจะต้องตัดสินว่าเชื่ออันไหน
>
> ราคาเดียวที่จ่ายคือไฟล์ครั้งถัดไปอาจใหญ่กว่าที่ผู้ใช้คาด ซึ่งเขาเห็นและกดสลับได้
   board แบบ linked ที่ไม่มีภาพวางเลย → ยังเป็น **v1** → รุ่นเก่าเปิดได้ตามเดิม
   board แบบ linked ที่มีภาพวาง → **v2** เพราะมันมี blob จริง ๆ อยู่ข้างใน

ได้ผลสามอย่างพร้อมกัน: ไม่มีทางเสียภาพที่วางไว้ · ไฟล์ linked ไม่โตโดยไม่จำเป็น ·
และปลดหนี้ตั้งแต่ P1-8 (ภาพจาก clipboard คมได้แค่ thumbnail) เพราะตอนนี้มันมีที่อยู่ถาวรแล้ว

#### ที่อยู่ของภาพที่วาง: `<data_local_dir>/pasted/<hash>.png`

`arboard` คืน RGBA ไม่ใช่ไบต์ของไฟล์ — จึงต้อง encode เป็น PNG ก่อนถึงจะฝังได้
**เขียนลง spool ตั้งแต่ตอน paste ทันที ไม่ใช่ตอน save**

| ได้อะไร | |
|---|---|
| ภาพมีไฟล์จริง | ขอ working texture ได้ทันที → **ปลดหนี้ P1-8 ตรงนั้นเลย ไม่ต้องรอ save** |
| `plan_embeds` ตอบ `Ours(path)` ได้ | ชั้น io ไม่ต้องรู้จัก encoder |
| เปิดไฟล์ packed → แตก blob กลับลง spool | สมมาตรทั้งสองทาง |

**อยู่ `data_local_dir` ไม่ใช่ `cache_dir`** — เหตุผลเดียวกับ `recovery/` เป๊ะ:
cache คือที่ของสิ่งที่สร้างใหม่ได้ · ภาพที่วางจาก clipboard **สร้างใหม่ไม่ได้จากอะไรเลย**
ถ้า cache eviction ลบมัน ผู้ใช้เสียภาพถาวร

ตั้งชื่อด้วย hash → ภาพเดียวกันวางซ้ำสิบครั้งได้ไฟล์เดียว

> ### ★★ กับดัก: spool ต้องอยู่นานเท่า recovery snapshot ที่อ้างถึงมัน
>
> snapshot ที่กู้คืนได้ **มีค่าเท่ากับ asset ที่มันอ้างถึงเท่านั้น**
> ถ้า spool ถูกเก็บกวาดไปแล้วแต่ snapshot ยังอยู่ → กู้คืนแล้วได้ board ที่เต็มไปด้วย `Missing`
> ซึ่งแย่กว่าไม่มี snapshot เลย เพราะผู้ใช้คิดว่ากู้ได้แล้วจริง ๆ
>
> **กติกาเก็บกวาด spool:**
> 1. ห้ามลบไฟล์ที่ **board ที่เปิดอยู่** อ้างถึง
> 2. ห้ามลบไฟล์ที่ **recovery snapshot ตัวใดก็ตามที่ยังอยู่ในโฟลเดอร์** อ้างถึง
>    > **แก้ 13 ส.ค. 2026** — ฉบับแรกเขียนว่า "snapshot ที่ยังไม่ถูกตอบ" ซึ่ง**แคบเกินไป**
>    > snapshot ที่ผู้ใช้ตอบว่า *"ทิ้ง"* ถูกลบไปแล้วจึงไม่อยู่ในรายการอยู่ดี
>    > แต่ตัวที่ตอบว่า **"เก็บไว้ก่อน ตัดสินใจทีหลัง"** ยังกู้ได้และยังอยู่ —
>    > ถือว่ามันจบแล้วจะทำให้**ตัวเลือกที่สามของ P4-4 กลายเป็นคำโกหก**
>    > (ผู้ใช้เลือกมันเพราะยังไม่แน่ใจ แล้วภาพหายไปเงียบ ๆ)
>    > → คุ้มครองทุกไฟล์ที่ยังอยู่ในโฟลเดอร์ ไม่ต้องแยกว่าตอบแล้วหรือยัง
> 3. ที่เหลือค่อยกวาด — **แต่เพดานต้องเป็นไบต์ ไม่ใช่จำนวนไฟล์** (แก้ 13 ส.ค. 2026)
>
>    วัดจริงแล้ว: clipboard 6000×4000 → **PNG 78 MB** (noise คือ worst case)
>    เพดานแบบนับไฟล์ 64 ตัว = **~5 GB** ซึ่งเต็มดิสก์ผู้ใช้เงียบ ๆ
>
>    | | |
>    |---|---|
>    | เพดานของไฟล์ที่**กวาดได้** | **512 MB** ไล่จากเก่าสุด |
>    | ไฟล์ที่ข้อ 1 หรือ 2 คุ้มครอง | **ไม่นับ ไม่ลบ ไม่ว่าใหญ่แค่ไหน** |
>
>    ★ ถ้าไฟล์ที่ถูกคุ้มครองอย่างเดียวก็เกิน 512 MB แล้ว → **บอกผู้ใช้ ห้ามลบ**
>    รูปแบบเดียวกับ "board เต็ม" ใน `ROADMAP P3-3` — เพดานต้องไม่กลายเป็นตัวทำงานหาย
>
>    **สถานะปกติจะเล็กมากอยู่แล้ว** เพราะพอ board ถูก save ภาพก็ไปอยู่ใน `.refx` แล้ว
>    ไฟล์ใน spool จึงกลายเป็นของซ้ำที่กวาดได้ทันที — spool ถือเฉพาะงานที่ยังไม่ถูกบันทึก

> ### ★ ต้องเป็น PNG เท่านั้น ห้ามบีบแบบสูญเสีย
>
> เคยคิดจะใช้ JPEG กับภาพที่ไม่มี alpha เพื่อลดขนาด — **ห้าม**
> ภาพที่วางจาก clipboard **ไม่มีต้นฉบับอยู่ที่อื่นเลย** ไฟล์ใน spool คือสำเนาเดียวที่มี
> บีบแบบสูญเสีย = ทำลายข้อมูลของผู้ใช้อย่างถาวรโดยที่เขาไม่มีทางกู้กลับ
> และเขาจะไม่รู้ตัวด้วย เพราะภาพยังดูใช้ได้
>
> ขนาดไฟล์เป็นเรื่องรอง — แก้ด้วยเพดานไบต์ข้างบน ไม่ใช่ด้วยการลดคุณภาพของสำเนาเดียวที่เหลือ
>
> ข้อ 2 คือข้อที่มองข้ามง่ายที่สุด และผลของมันคือ "กู้คืนสำเร็จแต่ภาพหายหมด"

> **การเขียน PNG ต้องไม่หน่วงการที่ภาพขึ้นจอ** — thumbnail สร้างจาก RGBA ที่มีอยู่ใน RAM แล้ว
> ส่วนการ encode ลง spool เป็นงานคู่ขนานบน worker (I-2) ภาพขนาด 6000×4000
> ใช้เวลา encode ระดับวินาที ผู้ใช้ต้องไม่รอ

> **ห้ามแก้ด้วยการเตือนผู้ใช้แล้วให้เลือกเอง** — คนที่วางภาพจากเบราว์เซอร์ไม่รู้ว่า
> "linked" กับ "packed" ต่างกันยังไง และการถามในจังหวะที่เขากำลังจะบันทึก
> คือการโยนการตัดสินใจที่เราควรตัดสินให้ ไปให้คนที่มีข้อมูลน้อยกว่า

### Relink เมื่อไฟล์หาย

1. ลองที่ path เดิม
2. ลองในโฟลเดอร์เดียวกับ `.refx` (เจอบ่อยสุดเวลาย้ายเครื่อง)
3. ค้นจาก `paths` table ใน cache DB ด้วย hash → ถ้าเจอที่อื่นบนเครื่อง ใช้เลย
4. ยังไม่เจอ → item เป็น `Missing` แสดง placeholder + ชื่อไฟล์ + ปุ่ม "หาไฟล์เอง"
5. ผู้ใช้ชี้ไฟล์ 1 ไฟล์ → ลองจับคู่ที่เหลือในโฟลเดอร์เดียวกันด้วย hash อัตโนมัติ

> ### ★ ซ่อมคีย์เก่าตอน relink สำเร็จเท่านั้น (ตัดสิน 19 ส.ค. 2026)
>
> ไฟล์ `.refx` ที่บันทึกก่อน 19 ส.ค. มี `AssetRef::hash` เป็น hash ของ **path**
> → ยุบไฟล์ซ้ำไม่ได้ และค้นด้วย hash ในขั้นที่ 3 ไม่เจอ
>
> **ห้ามซ่อมตอนเปิดไฟล์** — เอกสารเป็นแหล่งความจริงของตัวเอง การเขียนทับตอนเปิด
> คือการแก้งานผู้ใช้โดยเขาไม่ได้สั่ง และต้องผ่าน `Command` ด้วย
>
> **จังหวะที่ถูกคือตอน relink สำเร็จ** — ตรงนั้นเราเพิ่งอ่านไฟล์จริงจึงมี hash ของเนื้อในมือ
> ผู้ใช้เพิ่งสั่งให้ผูกใหม่ และผลลัพธ์ผ่าน `Command` อยู่แล้วจึง undo ได้
> ขั้นที่ 1 (เจอที่ path เดิม) ก็นับเป็นการ relink สำเร็จเหมือนกัน
>
> ระวัง: **ห้ามซ่อมคีย์ของภาพที่มาจาก clipboard** — ชื่อไฟล์ใน spool คือ hash ของ *พิกเซล*
> ส่วน hash ของไฟล์ PNG นั้นให้คนละค่า เขียนทับแล้วสองฝั่งจะชี้คนละ asset
> ทั้งที่เป็นภาพใบเดียวกัน

> `Missing` ต้องไม่หายไปจาก board และต้อง save กลับได้ครบ — ผู้ใช้ที่เปิดไฟล์บนเครื่องที่ไม่มีภาพ แล้ว save ทับ ต้องไม่เสียข้อมูลไป (I-3)

## 3. Versioning

mod v1 { pub struct BoardDto { /* ... */ } }
// อนาคต: mod v2 { ... }  + fn migrate_v1_to_v2(v1::BoardDto) -> v2::BoardDto

- DTO **แยกจาก type ใน `refx-core` เสมอ** — refactor ภายในต้องไม่ทำให้ไฟล์เก่าเปิดไม่ได้

## 4. Autosave & Journal (หัวใจของ I-3)

```
งานของผู้ใช้ = <ไฟล์ล่าสุดที่บันทึก> + <journal ที่ยังไม่ได้ apply>
```

> # ★★★ เปลี่ยนดีไซน์ 12 ส.ค. 2026 — v1 ใช้ **snapshot** ไม่ใช่ command journal
>
> ดีไซน์ journal ข้างล่างนี้ดีในหลักการ แต่ **`Command` เป็น trait ที่ serialize ไม่ได้**
> (`docs/02 §3` — มีแค่ `apply`/`undo`/`merge`/`affected`/`label`/`heap_size`/`as_any`)
> คำว่า "command payload" จึงยังไม่มีอยู่จริง ต้องสร้าง `CommandDto` 13 variant ขึ้นมาก่อน
>
> **เหตุผลที่ไม่เอา** — ไม่ใช่เพราะทำยาก แต่เพราะ**รูปร่างของความเสี่ยง**:
>
> | | command journal | snapshot |
> |---|---|---|
> | ผิวรูปแบบไฟล์ใหม่ที่ต้อง version/fuzz/round-trip | **เพิ่มอีกหนึ่งชุด** | **ศูนย์** — ใช้ DTO ของ P4-1 ตัวเดิม |
> | ภาระถาวรต่อ command ใหม่ทุกตัว | **มี** 13 variant และโตเรื่อย ๆ | ไม่มี |
> | ถ้าทำพลาดหนึ่งจุด ผู้ใช้ได้อะไร | **board ที่ผิดแบบเงียบ ๆ** | ไม่มีจุดให้พลาด |
> | เสียงานสูงสุด | 1 command | ≤ N วินาที |
> | ปริมาณเขียนดิสก์ | เบากว่ามาก | หนักกว่า (คุมด้วย dirty + rate limit) |
>
> แถวที่สามคือตัวตัดสิน — **"board ที่ผิดแบบเงียบ ๆ" แย่กว่า "เสียงาน 10 วินาที"**
> และเป็นรูปแบบความผิดพลาดที่โปรเจกต์นี้เจอซ้ำมาแล้วสิบกว่าครั้ง
> ส่วนการเสียงาน 10 วินาทีบน mood board = ลากภาพซ้ำสองใบ
>
> **v1 ทำแบบนี้แทน:**
>
> ```
> <doc>.refx.autosave     ← snapshot ทั้ง board ใช้ DTO เดียวกับ .refx เป๊ะ
> ```
>
> - เขียนด้วย `save_atomic` ตัวเดียวกับ P4-2 (tmp → fsync → rename)
> - **เขียนเมื่อ `dirty` เท่านั้น** และเว้นระยะอย่างน้อย N วินาที
>   → ผู้ใช้ที่เปิดดู reference เฉย ๆ = **ไม่มีการเขียนดิสก์เลย** (สอดคล้อง I-1)
> - บีบด้วย `zstd` (มีใน `docs/09` แล้ว)
> - **ลบเมื่อ save สำเร็จเท่านั้น**
> - ผูกกับเอกสารด้วย `doc_hash` เหมือนเดิม
>
> ### ★★★ งานที่ยังไม่เคยบันทึก ต้องมี autosave ด้วย (ตัดสิน 12 ส.ค. 2026)
>
> `<doc>.refx.autosave` ใช้ไม่ได้เมื่อยังไม่มี `<doc>` — แต่ **นั่นคือเคสที่อันตรายที่สุด**
> และเป็นตัวอย่างที่ `CLAUDE.md` ยกมาตรง ๆ: *"งาน mood board ที่จัดมา 3 ชั่วโมงหายไป
> เพราะ crash = เลิกใช้ทันที"* — คนที่จัดมาสามชั่วโมงโดยยังไม่เคยกด Ctrl+S
> คือคนที่เสียมากที่สุดและได้รับการปกป้องน้อยที่สุด
>
> **ที่อยู่: `<data_local_dir>/recovery/<session-id>.refx`**
>
> ★ **ต้องเป็น `ProjectDirs::data_local_dir()` ไม่ใช่ `data_dir()`** (แก้ 12 ส.ค. 2026)
> บน Windows `data_dir()` ชี้ไปที่ **Roaming** ซึ่งถูกซิงค์ขึ้นเซิร์ฟเวอร์ทุกครั้งที่ผู้ใช้
> ในโดเมนล็อกอิน → **งานที่ผู้ใช้ยังไม่เคยบันทึกจะถูกอัปโหลดขึ้นเครือข่ายองค์กร**
> โดยที่เขาไม่รู้ตัว และมันช้าด้วยเพราะ snapshot เขียนบ่อย
> `data_local_dir()` = `%LOCALAPPDATA%` ตามที่ต้องการ
>
> เจอเพราะรันของจริงแล้วเปิดโฟลเดอร์ดู — **เทสต์เขียวหมดก่อนหน้านั้น**
> เพราะไม่มีเทสต์ไหนถามว่า "โฟลเดอร์นี้ถูกซิงค์ขึ้นเน็ตไหม"
>
> **★ ห้ามวางใน `cache_dir` เด็ดขาด** — cache คือที่ของสิ่งที่สร้างใหม่ได้
> งานที่ยังไม่ได้บันทึกคือสิ่งตรงข้าม และ `docs/08 §5` มีกฎอยู่แล้วว่า cache eviction
> ห้ามแตะ `logs/` ด้วยเหตุผลเดียวกัน — recovery ยิ่งต้องไม่อยู่ในนั้น
>
> - `session-id` สุ่มตอนเปิดโปรแกรม → หลายหน้าต่างไม่ทับกัน
> - **ลบเมื่อผู้ใช้ Save ลง path จริงสำเร็จ** (ย้ายเจ้าของไปเป็น `<doc>.refx.autosave`)
> - ตอนเปิดโปรแกรม ไล่ดูโฟลเดอร์นี้ — เจอไฟล์ค้างจาก session ก่อน = แสดง dialog 3 ตัวเลือก
>   เหมือนกันทุกประการ ต่างแค่ข้อความบอกว่า *"งานที่ยังไม่เคยบันทึก"*
> - เก็บได้ไม่เกิน 10 ไฟล์ หรือ 30 วัน แล้วแต่อะไรถึงก่อน — มีเพดานตาม I-6
>   **แต่ห้ามลบไฟล์ที่ยังไม่เคยถูกถาม** ผู้ใช้ต้องได้เห็นก่อนเสมอ
>
> เกณฑ์ผ่าน: เปิดโปรแกรมใหม่ ลากภาพ **ไม่กด Ctrl+S เลย** แล้วฆ่าโปรเซส →
> เปิดใหม่ต้องได้งานคืน

> ### ★★★ "เก็บไว้ก่อน" ของเอกสาร ต้องเปลี่ยนชื่อไฟล์ (ตัดสิน 22 ส.ค. · รวมกล่องซ้ำ 24 ส.ค. 2026)
>
> *(เดิมมีสองกล่องเรื่องนี้ที่ชื่อไฟล์และกติกาเก็บกวาดขัดกันเอง — รวมเป็นกล่องเดียวแล้ว)*
>
> snapshot ของงานกำพร้าใน `recovery/` อยู่คนละไฟล์กับที่ autosave เขียน จึงรอดอยู่แล้ว
> แต่ snapshot ของ**เอกสารที่มี path** คือ `<doc>.refx.autosave` — **ไฟล์เดียวกัน**
> ที่ autosave จะเขียนทับในไม่กี่วินาที
>
> แปลว่าปุ่ม *"เก็บไว้ก่อน ตัดสินใจทีหลัง"* จะกลายเป็น *"ทิ้งใน 10 วินาที"*
> ซึ่งทำลายเหตุผลทั้งหมดที่ตัวเลือกที่สามมีอยู่
>
> **ทางที่เลือก: ย้ายไปเป็น `<doc>.refx.autosave.kept`** ตอนผู้ใช้กด "เก็บไว้ก่อน"
>
> | ทางเลือกที่ตกไป | ทำไม |
> |---|---|
> | หยุด autosave จนกว่าจะตอบ | เอา**งานใหม่**ไปเสี่ยงแทนงานเก่า — แลกของหายกับของหาย |
> | บอกความจริงบนปุ่ม/tooltip แล้วปล่อยให้ทับ | คนที่ไม่อ่านยังเสียของอยู่ดี · **คำเตือนไม่ใช่การป้องกัน** |
>
> **การเก็บทั้งสองอย่างดีกว่าการเลือกว่าจะเสียอันไหน** — ราคาคือชื่อไฟล์เพิ่มหนึ่งชื่อ
> ซึ่งถูกกว่าการเสียงานของผู้ใช้อย่างเทียบกันไม่ได้
>
> **กติกา:**
> - **ไม่ถูกลบอัตโนมัติเลย ไม่ว่ากรณีใด** — รวมถึงตอน save สำเร็จ
>   (ไฟล์ที่โผล่ข้างเอกสารเป็นสิ่งที่ผู้ใช้**สั่งให้เก็บไว้เอง** จึงไม่ใช่ขยะ)
> - ถูกเสนอกลับ**ทุกครั้งที่เปิดเอกสารนั้น** จนกว่าผู้ใช้จะกด *เอากลับมา* หรือ *ทิ้งไป*
> - **มีได้ไฟล์เดียวต่อเอกสาร** · กด "เก็บไว้ก่อน" ซ้ำ = ตัวใหม่ทับตัวเก่า
>   (ตัวใหม่ใหม่กว่าเสมอ จึงไม่มีอะไรหาย)
> - autosave ของ session ปัจจุบันยังเขียน `.autosave` ตามปกติ → **งานใหม่ไม่เสี่ยงเลย**
> - ที่กู้กลับมาแล้ว ลบได้**หลัง** snapshot ของ session นี้ลงดิสก์
>   (หลักการเดียวกับ `adopted_recovery` — ต้องมีสำเนาอยู่เสมอหนึ่งชุด)
>
> > ถ้ามีทั้ง `.kept` และ `.autosave` ตอนเปิด → เสนอ `.autosave` ก่อน (ใหม่กว่า)
> > แล้วค่อยเสนอ `.kept` หลังผู้ใช้ตอบตัวแรก — สองคำถามติดกันยอมรับได้
> > เพราะเกิดยากและทั้งสองอันคืองานของเขาจริง ๆ
> >
> > ★ **ทิ้งคำถามที่ค้างคิวเมื่อ `keep()` สำเร็จ** — ถ้าผู้ใช้ตอบ "เก็บไว้ก่อน" กับตัวใหม่กว่า
> > ขณะที่คำถามของ `.kept` ตัวเก่ายังค้างอยู่ ไฟล์ที่คำถามนั้นพูดถึงถูกเขียนทับไปแล้ว

> ### ★ snapshot ไม่ต้องมี `.bak`
>
> `save_atomic` ทิ้ง `.bak` ไว้เสมอ ซึ่งถูกสำหรับ**เอกสารของผู้ใช้** แต่ผิดสำหรับ snapshot —
> ได้ไฟล์ชื่อ `<doc>.refx.refx.bak` ที่ไม่มีใครอ่านและไม่มีใครกวาด โผล่อยู่ในโฟลเดอร์งาน
>
> snapshot คือสำเนาชั่วคราวที่ถูกเขียนทับทุกสิบวินาทีอยู่แล้ว **สำเนาของสำเนาไม่มีค่า**
> → เขียน snapshot ต้อง **ไม่สร้าง `.bak`** ตั้งแต่ต้น ไม่ใช่ไปตามลบทีหลัง

> **สิ่งที่ยกมาจากดีไซน์เดิมทั้งหมด ไม่เปลี่ยน:** `doc_hash` กันจับคู่ผิดไฟล์ · CRC ·
> ลบเมื่อ save สำเร็จเท่านั้น · **dialog กู้คืน 3 ตัวเลือก** (ตัวที่สามสำคัญที่สุด)
>
> **สิ่งที่ยอมเสีย:** undo history ข้าม session — หลังกู้คืนแล้ว Ctrl+Z ย้อนไปก่อน crash ไม่ได้
> ยอมรับได้ โปรแกรมส่วนใหญ่ก็เป็นแบบนี้
>
> **เมื่อไหร่ค่อยกลับมาทำ journal:** ถ้าวัดแล้วพบว่าการเขียน snapshot หนักเกินไปจริง
> (board ใหญ่ + แก้ถี่) หรือมีผู้ใช้รายงานว่าเสียงานที่มีความหมาย
> ตอนนั้นค่อยทำ พร้อม `CommandDto` ที่บังคับด้วย exhaustive match ให้คอมไพล์ไม่ผ่าน
> ถ้ามีใครเพิ่ม command แล้วลืม — **ห้ามทำโดยไม่มีการบังคับตอนคอมไพล์**

### Journal

`<doc>.refx.journal` — append-only ข้าง ๆ ไฟล์เอกสาร

```
[magic "RFXJ"][doc_hash: 32B]           ← ผูกกับเอกสารตัวไหน กัน journal ผิดคู่
แล้วต่อด้วยหลาย record:
[seq: u64][len: u32][crc: u32][command payload]
```

- เขียนต่อท้ายทุกครั้งที่ apply command สำเร็จ
- `fsync` ทุก 2 วินาที หรือทุก 20 record แล้วแต่อะไรถึงก่อน (ไม่ fsync ทุกครั้ง — จะช้าจนใช้ไม่ได้ตอนลากเมาส์)
- record ที่ท้ายไฟล์ CRC ไม่ผ่าน = ตัดทิ้ง (ไฟฟ้าดับกลางเขียน — เป็นเรื่องปกติ ไม่ใช่ข้อผิดพลาด)
- ลบ journal เมื่อ save สำเร็จเท่านั้น

</details>

### Save แบบ atomic

```rust
let tmp = path.with_extension("refx.tmp");
{ let f = File::create(&tmp)?; write_all(&f)?; f.sync_all()?; }   // ★ fsync ก่อน rename
fs::rename(&tmp, path)?;                                          // atomic ในทุก OS
sync_dir(path.parent())?;                                         // Linux ต้อง fsync directory ด้วย
fs::remove_file(journal_path).ok();
```

**ห้ามเปิดไฟล์เดิมด้วย `File::create` แล้วเขียนทับ** — ถ้าตายกลางทาง งานของผู้ใช้หายทั้งหมด นี่คือวิธีที่โปรแกรมทำข้อมูลผู้ใช้หายบ่อยที่สุด

### Recovery ตอนเปิดโปรแกรม

```
เจอ journal ที่ doc_hash ตรงกับไฟล์ที่กำลังเปิด

## 6. Import / Export

**Import:** drag & drop ไฟล์หรือโฟลเดอร์, paste จาก clipboard, เปิด `.refx`
**Export:**
- PNG/JPEG ของทั้ง board (render off-screen ตามขนาดที่เลือก, มี cap ที่ 16384 px)
- คัดลอกภาพที่เลือกไปโฟลเดอร์
- `.refx` packed สำหรับส่งต่อ

Export ภาพขนาดใหญ่ต้องทำเป็น tile (render ทีละ 4096×4096 แล้วต่อกัน) ไม่งั้นชน texture size limit ของ GPU และ OOM

### ★ รายละเอียด Export (เขียนไว้ก่อน P5-4 · 6 ก.ย. 2026)

#### หน่วยความจำคือข้อจำกัดจริง ไม่ใช่ texture limit

16384 × 16384 × RGBA = **1 GB** ในบัฟเฟอร์เดียว — ทะลุงบทุกข้อ
→ **ห้ามประกอบภาพเต็มใน RAM แล้วค่อยเข้ารหัส**

| | |
|---|---|
| render | tile 4096×4096 |
| ส่งเข้าตัวเข้ารหัส | ทีละ **แถบ** (band) ตามลำดับบรรทัด |
| ★ เพดาน RAM ตอน export | **ค่าคงที่ ไม่ขึ้นกับขนาดที่ผู้ใช้เลือก** |

> ### ✅ วัดแล้ว 7 ก.ย. 2026 — **ทั้งสองรูปแบบสตรีมได้**
>
> | ทาง | 4096² | 8192² | 16384² |
> |---|---|---|---|
> | `image` PNG บัฟเฟอร์เต็ม | 223 MB | 877 MB | ~3.4 GB |
> | `png::StreamWriter` แถบ 256 | **8.7 MB** | **12.8 MB** | **20.8 MB** |
> | `image` JPEG บัฟเฟอร์เต็ม | 52 MB | 196 MB | ~780 MB |
> | JPEG `encode_image` แถบ 256 | **7.2 MB** | **10.2 MB** | **16.2 MB** |
>
> ★ JPEG พิสูจน์ด้วยตัวป้อนที่**จดว่าถูกขอย้อนหลังกี่แถว** — `worst_backwards = 0`
> ทุกขนาดแถบที่ลอง และ `fills` เท่ากับจำนวนแถบพอดี = อ่านแต่ละพิกเซลครั้งเดียวจริง
> **ไม่ได้เชื่อเอกสารของ crate** (`docs/08 §3.9 ข้อ 1`)
>
> ผลพลอยได้: PNG แบบแถบ **เร็วกว่า** แบบเต็ม (202 vs 244 ms ที่ 4096²)

#### ★★ เพดาน RAM: แถบกิน **O(ความกว้าง)** ไม่ใช่ค่าคงที่

`band_rows = BAND_BUDGET / (width × bpp)` · **พื้นล่าง 8 แถว** (บล็อกของ JPEG)
เพดานบน 1024 แถว — สูงกว่านั้นไม่ได้อะไรเพิ่ม

| | ค่า |
|---|---|
| `BAND_BUDGET` | **32 MB** |
| tile ที่ render ต่อครั้ง | กว้าง ≤ 4096 × สูง = `band_rows` — **ทรงแถบ ไม่ใช่จตุรัส** |
| **เพดานรวมที่ต้องพิสูจน์** | บัฟเฟอร์แถบ + staging ของ readback **รวมกัน ≤ 64 MB** |

> ★ ตัวเลขที่วัดไว้ข้างบนเป็นฝั่ง CPU ล้วน · **ทางอ่านกลับจาก GPU ยังไม่ถูกวัด**
> tile 4096² RGBA = **67 MB** ซึ่งใหญ่กว่าบัฟเฟอร์แถบทั้งก้อน
> → จึงต้องเป็น tile ทรงแถบ · และเพดานต้องพิสูจน์ด้วย **RSS จริงตอน export**
> ไม่ใช่ผลรวมบนกระดาษ

#### กฎที่ห้ามละเมิด

1. **I-2** — งาน render + encode อยู่ที่ worker · UI ต้องลากหน้าต่างได้ระหว่าง export
2. **ยกเลิกได้ทุกเมื่อ** พร้อม cancellation token · ยกเลิกแล้ว**ต้องไม่เหลือไฟล์ครึ่งใบ**
3. **I-3 / เขียนแบบ atomic** — เขียนลงไฟล์ชั่วคราวข้างปลายทาง แล้ว rename
   **ห้ามแตะไฟล์ปลายทางจนกว่าจะเข้ารหัสเสร็จ** · ผู้ใช้ export ทับไฟล์เดิมแล้วยกเลิกกลางคัน
   ต้องได้ไฟล์เดิมครบ ไม่ใช่ไฟล์เสีย
4. **ทับไฟล์ที่มีอยู่ = ถามก่อน** · path ผ่าน **`validate_save_target()`**
   — ★ **ไม่ใช่ `validate_asset_path()`** ซึ่งเป็นด่านของ path ที่มาจากไฟล์
   และจะปฏิเสธไดรฟ์ที่แชร์ไว้ · ดู `docs/06 §4` (แก้ 8 ก.ย. 2026 — สเปกเดิมผิด)
   · **หลัง rename ต้องอ่านขนาดกลับมายืนยันว่าไฟล์ลงจริง**
5. **board ว่าง = ปฏิเสธพร้อมบอกเหตุผล** ห้ามเขียนไฟล์ 0 ไบต์
6. **I-7** — ภาพเสียหนึ่งใบห้ามล้ม export ทั้งงาน

#### สิ่งที่ผู้ใช้ต้องเห็นก่อนกดจริง

ขนาดพิกเซลที่จะได้ · ประมาณขนาดไฟล์ · **จำนวน item ที่เป็น `Missing`**

> ### ★★ `Missing` ต้องเตือน ไม่ใช่เงียบ
> export คือสิ่งที่ผู้ใช้ส่งให้คนอื่น · ถ้าภาพหายไปสามใบแล้วรู้ทีหลัง
> คือความเสียหายที่ย้อนไม่ได้ · **สิ่งที่เห็นบนแคนวาสคือสิ่งที่ได้ (WYSIWYG)**
> แต่ต้องบอกจำนวนก่อน แล้วให้ยกเลิกได้

#### สิ่งที่ต้องออกมาถูก

> ### ★★★ การยกเลิกต้องเกิดที่ **ปลายทาง** ไม่ใช่ที่ลูปของเรา (บันทึก 8 ก.ย. 2026)
> JPEG เป็นตัวเข้ารหัสแบบ **ดึง** — ถ้ารอเช็คธงที่ลูปของเรา มันจะไล่ขอพิกเซล
> จนจบภาพก่อน (16384² = **268 ล้านครั้ง**) แล้วผู้ใช้ที่กดยกเลิกจะเห็นโปรแกรม
> นิ่งไปอีกครึ่งนาที → ธงต้องถูกอ่านใน **ตัวป้อนพิกเซล** ที่ตัวเข้ารหัสเรียก
>
> กฎทั่วไป: **ใครเป็นคนคุมลูป คนนั้นคือที่ที่ต้องเช็คการยกเลิก**

> ### ★ สีพื้นต้องแปลง sRGB → linear ก่อน `Clear`
> เป้าเป็น `Rgba8UnormSrgb` · ไม่แปลง = เทา 50% ออกมาสว่างเกิน
> **และขาวกับดำมองไม่เห็นข้อผิดนี้** — เทสต์สีพื้นต้องใช้เทากลาง
> (`docs/08 §3.9 ข้อ 1b`: input ต้องเป็นค่าที่ *แสดงความผิดได้*)

grayscale · flip · opacity · rotation ต้องผ่านเส้นทาง shader **เดียวกับที่วาดบนจอ**
→ ห้ามมีเส้นทางวาดสำหรับ export แยกต่างหาก ไม่งั้นมันจะเพี้ยนจากจอเงียบ ๆ

| รูปแบบ | พื้นหลัง |
|---|---|
| PNG | โปร่งใสได้ (ให้เลือก) |
| JPEG | ไม่มี alpha → **ต้องประกอบลงสีพื้นที่เลือกไว้** ห้ามได้พื้นดำโดยไม่ได้ตั้งใจ |
